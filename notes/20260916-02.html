一次 tool-call 错误的排查记录

最开始看起来像模型没有按要求调用工具。把请求历史和流式响应拆开以后，才发现问题往往出在客户端的拼接：工具调用还没收齐，历史里的字段又被丢了一部分。

下面的例子都做了缩短和脱敏，排查顺序对应 deepseek-protocol-doctor 现在实际检查的内容。

先看请求历史，不先怪模型

tool calling 不是在一段普通对话里多塞一个字段。一轮完整的历史大概是：用户提出问题，assistant 返回工具调用，客户端执行工具，再把带有同一个 tool_call_id 的 tool 消息放回去，最后 assistant 才继续回答。

所以我先把失败请求压成一个最小例子。assistant 叫了 call_weather_1，下一条 tool 消息却回了另一个 id；如果前一个调用的参数还没收完，后面又开始新一轮消息，也会把这条链打断。

{
  "role": "assistant",
  "reasoning_content": "The user needs a weather lookup.",
  "tool_calls": [{
    "id": "call_weather_1",
    "type": "function",
    "function": {
      "name": "get_weather",
      "arguments": "{\"location\":\"Hangzhou\"}"
    }
  }]
}
{
  "role": "tool",
  "tool_call_id": "call_weather_1",
  "content": "24°C and sunny"
}

真正容易漏掉的是 reasoning_content。打开 thinking 时，assistant 的工具调用消息不只包含 tool_calls，还需要保留模型原样返回的 reasoning 字段。很多客户端在把响应重新写回 history 时，只留下了看起来更熟悉的内容和工具调用，把这个字段丢了。下一次请求的 JSON 形式仍然像是对的，DeepSeek 却可能直接拒绝。

这时候不能临时拼一段“我刚才思考了……”的假内容。那样只是把一个可定位的字段丢失，变成了写回会话的错误内容。正确做法是保留原值；如果确实不使用 thinking，就在请求里明确关闭，而不是让客户端和服务端各自猜。

再看 SSE：一行不等于一次调用

流式响应更容易把人带偏。每个 data: 只是一个 delta，工具名、调用 id 和参数字符串可能分散在不同片段里。一个完整的参数可能长这样：

data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"q\""}}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":":\"x\"}"}}]}}]}

如果只有一个调用，按到达顺序追加似乎也能工作。但多个调用的 delta 可以交错到达。比如先收到 index 0 的 {"q"，再收到 index 1 的 {"q"，然后才分别收到后半段。客户端如果把所有片段放进同一个字符串，最后看到的就不是两个 JSON，而是一串谁也解析不了的半成品。

因此拼接的主键不是“这条消息什么时候到”，而是流里明确给出的 tool_calls[].index。先按 index 建桶，再在每个桶里追加 function.arguments。等到参数收齐之后再解析 JSON。仓库里的交错流 fixture 就是专门用来守住这个边界的。

还有两个看起来奇怪、但不应该被误判的片段：有些流会发 function.arguments: null，后面再继续给字符串；最后还可能有一个 choices: [] 的 usage chunk。前者要记下来但不能让它把后续字符串吞掉，后者是信息，不是工具调用失败。

reasoning_content 是怎么丢的

我后来把这件事分成三个边界来看：

  1. 模型返回的边界：SSE delta 里可能分开给出 reasoning、普通 content 和 tool-call delta。
  2. 客户端合并的边界：工具参数需要按 index 归并，reasoning 则需要按原始顺序保留下来。
  3. 下一次请求的边界：assistant 的上一条工具调用和后续 tool 结果必须带着同一组 id、参数和 thinking 配置回去。

只看最终 UI 往往看不出是哪一层坏了。界面可能显示“正在调用天气工具”，日志也可能显示工具真的执行过了，但真正发给下一次请求的 history 已经没有 reasoning_content，或者 tool 结果对应不上原来的调用。于是错误看起来像模型不稳定，实际上是协议状态被客户端重建错了。

所以我做了 deepseek-protocol-doctor

我需要的不是另一个会替我调用模型的 Agent，而是一个离线的“先把线捋顺”的检查器。手上已经有 request JSON、保存下来的 SSE 或 JSONL，就应该先检查这些材料，而不是每次都重新请求一次，靠运气看它会不会再错。

deepseek-protocol-doctor 现在把检查分成两条线：

  • check 看请求历史：tool call id 是否能对应，tool 结果有没有提前或漏掉，thinking 是否明确，原始 reasoning_content 是否还在，严格 schema 和 max_tokens 有没有明显问题。
  • stream 看保存的 SSE / JSONL：每行是不是 JSON，choices 和 delta 的形状是否合理，多个 index 是否交错，arguments 拼完后是不是对象，流是否正常结束。

每个发现都有固定的 code，例如 REASONING_CONTENT_MISSING、TOOL_RESULT_ORPHAN、SSE_TOOL_ARGUMENTS_INVALID 和 SSE_TOOL_INDICES_INTERLEAVED。这样修完之后可以再跑一遍，也可以把结果接进 CI，而不是只留一句“这次好像又好了”。

它不会判断回答质量，也不会假装自己知道模型到底想了什么；它只对给定的请求和响应做静态检查。这个边界反而比较重要：协议错误可以复现，模型好不好用则是另一件事。

现在的排查顺序

  1. 保存原始 request 和原始 SSE / JSONL，不要只截最终页面。
  2. 先脱敏，再分别跑 dsv4-doctor check request.json --format json 和 dsv4-doctor stream response.jsonl。
  3. 先处理 error，再看 warning 和 info；尤其先确认 id、index、reasoning_content 这三条链。
  4. 修客户端的合并或重放逻辑，重新保存一份最小 capture，再跑同样的检查。

这套顺序没有什么神秘的地方。只是把“模型抽风”拆成几段普通的数据结构问题：一段消息历史、一组调用 id、几条流片段，以及一个必须原样带回去的字段。拆开以后，至少知道下一步该看哪里。

项目代码、fixture 和测试在 deepseek-protocol-doctor。它是一个第三方离线检查器，不是 DeepSeek 官方组件。
