把中转站接通之后：Request timeout、403 与协议错误

Codex CLI 接入中转线路时，API 地址、请求链路和认证状态需要分别检查。

Codex CLI、CC Switch、RelayQuill 和 mihomo 的配置记录。

请求链路

请求链路通常为：Codex CLI → 本机的 127.0.0.1:8317 → 中转服务 → 上游模型。mihomo 可能作为网络出口。检测到 127.0.0.1:8317，只能说明 Codex 已连接本地中转；是否使用代理，需要检查中转进程的网络配置。

CC Switch 用于切换 profile。RelayQuill 的 Base URL 应为 /v1，协议为 Responses，模型为 gpt-5.6-luna。模型字段只填写模型 ID，不能附加 /responses。

错误处理

  • Request timeout / Reconnecting：先看本地 8317 是否监听，再看中转到上游是否超时。
  • 401 invalid management key：管理 API 密钥不匹配。该密钥与 RelayQuill API Key 分开配置；如果服务端仍启用鉴权，管理密码留空会失败。
  • 503 auth_unavailable：本地中转收到了请求，但没有可用认证。检查 profile 的 API Key、Base URL 和协议。
  • 403 Country, region, or territory not supported：请求走了官方登录或 token 刷新，官方上游拒绝当前出口地区。
  • 403 This account only allows Codex official clients：上游账号只接受官方 Codex 客户端，拒绝 OpenAI-compatible 的 Responses 转发。需要允许 API/relay 的账号，或使用官方 profile。
  • 协议错误 / 404：核对 Base URL、Responses 协议和模型 ID。Base URL 不要包含完整请求路径。

最短的现场检查

export PATH="$HOME/.local/bin:$PATH"
ss -lntp | grep 8317
curl -sS --max-time 15 -o /dev/null -w "local relay: HTTP %{http_code}\n" http://127.0.0.1:8317/v1/models
curl -sS --max-time 15 -o /dev/null -w "upstream: HTTP %{http_code}\n" https://api.relayquill.com/v1/models

8317 没有监听，先处理本地中转。若本地有响应、外部请求超时，再查 mihomo 的端口，以及中转进程是否继承了代理环境变量。

切换 profile 后如何找回旧聊天

切换 profile 只改变后续请求使用的供应商和认证配置。聊天记录在本地 Codex session 中。只要 $CODEX_HOME 没变（默认是 ~/.codex），可以运行：

codex resume --last

直接运行 wrapper 通常会新开会话。切换后出现“原模型和当前模型不同”的提示是正常的。记录会保存模型或供应商信息，但这不等同于账号用户名。

安全

API Key 不要放进文章、.bashrc 或命令历史。曾经粘贴到聊天或日志里的 Key，应该撤销后重新创建。中转服务的 management key 和 API Key 分开管理；空密码只适合隔离的本机测试。
